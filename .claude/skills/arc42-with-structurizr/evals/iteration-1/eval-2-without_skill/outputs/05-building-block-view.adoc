[[white-box-legacy-monolith]]
==== Whitebox — Monolith

Der Monolith ist ein Abhängigkeitsgraph zur Compilezeit, keine Menge von Laufzeitservices. `atu-gui` hängt von `atu-app` ab, dieses von `atu-objrel`; 1.007 GUI-Dateien umgehen die Serviceschicht und greifen direkt auf `atu-objrel` zu — genau das macht die Extraktion teuer.

image::../diagrams/05-whitebox-monolith.svg[Whitebox Monolith, pdfwidth=80%, align=center]
[cols="3*", options="header"]
|===
| Baustein | Verantwortlichkeit | Zukunft

| `atu-objrel` | Eigenes ORM (`com.topf.objrel`) — Sessions, Abfragen, Persistenz | Domäne für Domäne durch JPA/Hibernate ersetzt
| `atu-app` | 964 Domänenobjekte auf ObjRel | Ersetzt durch JPA-Entities in `atu-domain-*`
| `atu-gui` | 1.193 Servlet-Klassen, die HTTP, Datenbankzugriff und HTML vermischen | Ersetzt durch REST-Ressourcen in `atu-api-*` + Angular-SPA
| `atu-html` / `atu-objrelhtml` | Serverseitiges Rendering von HTML-Komponenten | Entfällt, sobald die letzte Servlet-Oberfläche abgelöst ist
| `atu-encashment`, `atu-stat` | Zahlungsverarbeitung, OLAP-Statistiken | Werden zu `atu-domain-encashment` / `atu-domain-reporting`
| `atu-cust-*` | Konfiguration, Verhaltensüberschreibungen und Custom Code je Mandant — einkompiliert | Aufgeteilt in Typ-1/2-Konfiguration und Typ-3-Plugin-JARs (<<tenant-variation-model-three-types>>)
|===

[[white-box-new-domain-services]]
==== Whitebox — Neue Domänenservices

image::../diagrams/05-whitebox-new-domain-services.svg[Whitebox neue Domänenservices, pdfwidth=90%, align=center]
*Die Deployment-Einheiten sind die `atu-api-*`-Runner* — einer je Domäne, jeder bedient alle 17 Mandanten. `atu-domain-*` und `atu-cust-*` sind Bibliotheken, die *in* diese Runner paketiert werden; keine von beiden wird eigenständig deployt.

Die vollständigen Detaildiagramme finden sich in `architecture-concept.adoc`, Abschnitte „Current State Architecture" und „Target Gradle Modules".

[[white-box-a-single-domain-service]]
==== Whitebox — Ein einzelner Domänenservice

Jeder `atu-api-*`-Runner besitzt dieselbe innere Schichtung (<<adr-009,ADR-009>>). Encashment dient als repräsentatives Beispiel; die anderen fünf sind strukturell identisch.

[[component-encashment]]
===== Component-Diagramm — Encashment-Service (C3)

image::../diagrams/05-component-encashment.svg[Component-Diagramm Encashment, pdfwidth=80%, align=center]

image::../diagrams/05-whitebox-single-domain-service.svg[Einzelner Domänenservice, pdfwidth=80%, align=center]
[cols="3*", options="header"]
|===
| Schicht | Verantwortlichkeit | Darf nicht

| API | JAX-RS-Ressourcen, DTO-Mapping, Übersetzung von HTTP-Status und Fehlern, `@RolesAllowed` | Geschäftsregeln enthalten oder den `EntityManager` berühren
| Domäne | Geschäftsregeln, Transaktionsgrenzen, Auswahl der Erweiterungspunkte | HTTP- oder JAX-RS-Typen kennen
| Modell | JPA-Entities, Repositories, Abfragen | Logik zum Mandanten-Routing enthalten
| Infrastruktur | `TenantResolver`, `MultiTenantConnectionProvider`, Auswahl der Datasource | Von API oder Domäne anders als über das Framework erreichbar sein
|===

*Nahtstelle für die Mandantenvariation:* Die Domänenschicht hängt von einer *Schnittstelle* mit einer in `atu-domain-*` mitgelieferten Default-Implementierung ab. Ein Mandanten-Plugin-JAR steuert eine `@Identifier`-qualifizierte Alternative bei. Beim Deployment je Domäne (<<adr-006a,ADR-006a>>) liegen alle 17 Plugin-Sätze im Classpath jedes Runners, weshalb die `@Identifier`-Auswahl tragend ist — sie bestimmt je Anfrage das richtige Bean. Das ist der eine Mechanismus, der sich mit <<adr-006a,ADR-006a>> geändert hat; im abgelösten Modell je Mandant *war* der Runner der Mandant, und es war keine Auswahl nötig.
